## 2. Prompt 1 — CV keyword extraction

**Design rationale.** Three constraints drove this prompt:

1. **Schema-constrained output.** `format=json` restricts decoding to valid JSON, and the schema is repeated in the prompt. This removed almost all parse failures across 110 documents.

2. **An asymmetric schema.** A CV reports what a person *did*; a JD reports what a role *requires*. Forcing both into one bag of words discards the must-have / nice-to-have distinction, which is the single strongest signal a recruiter uses.

3. **Explicit anti-hallucination rules.** The model is told not to invent skills, to cap list length, and to use canonical short names. Post-processing then enforces this deterministically.


**Worked example — `CV-001`** (latency 6.50 s)

## 3. Prompt 2 — JD keyword extraction

**Design rationale.** The JD prompt differs from the CV prompt in two ways that matter. First, it asks the model to *separate* must-have from nice-to-have, because the retriever weights those differently. Second, it tells the model to ignore perks, benefits and application-question boilerplate — without that instruction roughly a fifth of extracted “requirements” were things like “health insurance” and “maternity leave”.

## 4. Prompt 3 — keyword merge adjudication

**Design rationale.** Asked simply to “group similar skills”, the model reliably merges `mysql` into `sql` and `pytorch` into `machine learning`. Those merges destroy exactly the signal that separates candidates. The prompt therefore contains explicit negative rules and requires a written justification per group; a lexical head-noun guard and an embedding veto then filter the proposals (see §4 of the report).

## 5. Prompt 4 — ground-truth adjudication

**Design rationale.** This is the most delicate prompt in the project, because the ground truth determines every number in the report. Two earlier designs were rejected after inspection (documented in §2 of the report):

- **v1** asked for an absolute 0–3 fit score. The model returned grade 2 with reasons like *“but lacks AI focus and customer collaboration”* — the label contradicted its own justification.

- **v2** added a self-consistency cap, which over-corrected and collapsed the relevant set.


The final design replaces an absolute judgement — which an 8B model cannot calibrate — with two things it can do reliably:

1. a **profession gate** (“is this person in this line of work at all?”), a near-binary question, enforced mechanically in code;

2. a **reference-anchored comparison** against the CV of the person actually hired, which is a comparative judgement against a concrete example rather than an abstract rubric.


**Worked example — `P01` × `CV-075`** (graded 2)

System prompt:

```text
You are a senior technical recruiter. You compare one candidate with the person the client actually hired for the same vacancy, and you place the candidate on the client's bar. You judge only what the work history demonstrates, and you do not let a job title substitute for evidence. Return strict JSON only.
```

## 6. Prompt 5 — second annotator (agreement study)

Deliberately different rubric, different sample, different seed. The purpose is not to improve the labels but to measure whether they reproduce. See `scripts/03b_second_annotator.py` for the full text.

```text

Read the vacancy and the candidate CV, then decide how this candidate
compares with the person the company hired for this vacancy last time.

VACANCY / PERSON HIRED / CANDIDATE  (full texts inserted)

First decide whether the candidate works in the same line of work as the
vacancy. If not, the answer is 0. If they do, grade them against the
hired person:
  0 = different line of work
  1 = same line of work, but clearly weaker than the person hired
  2 = same line of work, close enough to be worth an interview
  3 = same line of work, as strong as or stronger than the person hired
```

## 7. Prompts used to direct the coding assistant

The assignment is as much about directing an AI assistant as about the model itself, so the working prompts are recorded here.

### 7.1 Initial scoping

```text

Below is the instruction of assignment4;

[verbatim assignment text: unzip the dataset; apply a local LLM
(ollama, qwen3:8b) to extract keywords from CV and JD; merge/cluster
similar keywords; build an AE model to encode the CV and JD; for each
JD in the ground truth locate the top 10 CVs; measure the Recall of
the search; conduct error analysis for potential improvements]

goal: perform the best recall result and error analysis result as best
as you can

Submittion: 1. HTML ... 2. a pdf format report 3. the prompt transcript
4. the code
```

**What I asked for and why.** The instruction left the ground truth undefined, so the first substantive question to the assistant was how to evaluate at all. That turned out to be the crux of the whole assignment.

### 7.2 The critical follow-up: is the hired CV in the pool?

```text

Check whether each of the 10 hired CVs appears anywhere in the 100-CV
pool. Compare exact text, 8-gram shingles, and employer strings. Report
the maximum overlap per hired CV.
```

This returned **zero** overlap for all ten. It is the single most important finding in the project: it means “recall” cannot mean “did we find the hired person”, and the task is relevance retrieval against constructed labels.

### 7.3 Diagnosing the autoencoder

```text

The AE reconstructs the keyword block with F1 = 0.997 but its latent
neighbours are nonsense (Data Engineer JD nearest a Graphic Designer).
Measure latent-space purity against job family for: the input space
itself, and several AE configs. Tell me whether the AE is compressing
structure or destroying it.
```

This produced the 06b–06g diagnostic series, which found that the input space (purity 0.36) beats every MSE-trained AE, that a cosine reconstruction loss recovers most of the gap (0.30), and that adding the domain or text blocks makes it worse. Those negative results are reported rather than hidden.

### 7.4 Calibrating the judge

```text

The judge is giving grade 2 to CVs whose own stated reason says they
lack the core requirements, and it grades a Founder/Author as a strong
UI/UX match. Rewrite the adjudication prompt so the profession gate is
asked first and enforced in code, and so the fit question is anchored
to the hired CV instead of an abstract rubric.
```

## 10. Where the pipeline's own prompts were rewritten

Four prompt designs in this project were discarded after inspecting their output. Each rewrite is recorded because the *failure* is the interesting part, and because a report that only shows the final prompt hides how much of the work was calibration:

| prompt | problem observed | change |
|---|---|---|
| ground-truth v1 | grade 2 returned alongside a reason saying the candidate *lacked* the core requirements | added a self-consistency rule |
| ground-truth v2 | the self-consistency rule used the first six must-haves, which for P01 were rare manufacturing-costing terms; every real finance CV scored 1 | replaced the requirement list with a comparison against the hired CV |
| ground-truth v3 | the LLM profession gate classified a Principal Product Manager as “engineering” and left two JDs with an empty relevant set | moved the gate out of the model into deterministic code; kept the LLM for grading within the gate |
| keyword merge | the model merged `mysql` into `sql` and `pytorch` into `machine learning` | added explicit negative rules, a written justification requirement, an embedding veto and a head-noun guard |

Each of these was caught by reading the model's output, not by a metric. That is the practical lesson of using an 8B local model: the numbers will look plausible even when the labels are wrong, so the outputs have to be inspected.
